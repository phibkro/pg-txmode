Status: **spec** (frozen when its PR opens). Date: 2026-10-29. Decided by: the operator's assignment of 2026-10-29 (build `phibkro/pg-txmode`: a client-neutral core with thin adapters, from the research report `REPORT.md` and its `probes/`).
Process: [spec 0000](0000-development-lifecycle.md). Stacked on the branch of PR #1 (spec 0000).
Verify skill: `verify-pg-txmode` (updated in this PR: it now runs the harness).

## Problem

A transaction pooler (Cloudflare Hyperdrive, PgBouncer in transaction mode, Supavisor) breaks PostgreSQL features that live in a session, and mostly **without an error**: a `SET` shows up in another client, a session advisory lock excludes nobody, a named prepared statement runs another client's SQL. The facts are in at least six places that disagree (the research report, section 3 and 4), every ecosystem has a per-driver switch and none has a type, a conformance suite or a lint. Local development never meets the pooler (Hyperdrive's local mode connects directly), so the first run through it is production.

## Goal

A library with no Effect and no driver in its core, in four packages, that makes the facts one data file, the safe behaviour the only easy behaviour, and the unsafe behaviour a failing test:

| Package | Journey it gives |
| --- | --- |
| `@pg-txmode/core` | read the catalogue; pick a connection mode and get its capabilities; get the SQL for a safe construct; classify an SQLSTATE; open a transaction with timeouts in one round trip; retry a whole transaction |
| `@pg-txmode/harness` | `bun run probes` starts PostgreSQL 18 and PgBouncer (Neon's settings) and prints what every probe observed against the catalogue; a client can be put through the same probes |
| `@pg-txmode/lint` | `pg-txmode-lint --mode hyperdrive src/ --log run.ndjson` reports pooler-unsafe SQL in `.sql` files, `sql` templates and a recorded statement log |

## Journey

```text
bun install
bun run probes        → 23 probes, each: direct (control) vs PgBouncer, compared to the catalogue row that names it
bun run docs:gen      → README table regenerated from packages/core/src/catalogue.ts
bun run stack         → PostgreSQL :54320 and PgBouncer :64320 for your own client (what `devenv up` runs)
bun packages/lint/src/cli.ts --mode hyperdrive <paths> [--log file.ndjson]
```

In code: `capabilities(hyperdrive).sessionAdvisoryLock` is `"no"`, computed from the catalogue; `requireFeature(hyperdrive, "listen")` throws with the catalogue row, its note and its sources; `SessionApi<TransactionPooledMode, X>` is `never`.

## Constraints and values

- **One source per fact.** The catalogue is one TypeScript data file. The README table is generated from it (`bun run docs:gen`; `bun run check:docs` and a test fail on drift). Capabilities are computed from it. Lint messages quote it. A probe is tied to its row by id, in both directions, by a test.
- **Every cell says how it is known** (`docs`, `pgbouncer-probe`, `hyperdrive-probe`, `unverified`) and every row has a primary source URL. `unknown` is never verified. `hyperdrive-probe` needs a recorded run that this repository holds (`docs/evidence/hyperdrive/`). This repository has no Hyperdrive probe of its own: the Worker needs the operator's Cloudflare credentials, so its steps are a wizard (`docs/wizard/hyperdrive-probe.md`), not run.
- **An unverified behaviour is not a safe one.** `capabilities` returns `unverified` for it, `requireFeature` refuses it unless the caller accepts it, and the lint warns.
- **Plain SQL, not a query builder.** The constructs are SQL strings with an executable test each.
- **The core has no dependencies** (Effect boundary test, spec 0000). Node-only code (`libpg-query`, `oxc-parser`, the servers) is in the lint and the harness.
- **A probe is a measurement, not a hope.** Each runs against PostgreSQL (the control) and against a fresh PgBouncer with Neon's published settings, and the two observations must equal the catalogue's two cells.

## Constraints on the implementation

- Free on mechanism, specific on behaviour: the data structures, the AST walk and the probe code may change as long as the journey and the falsifiers hold.
- The harness starts its own servers on free ports; no test needs `devenv up`.
- Tests that wait for the server's own timers (idle-in-transaction, transaction timeout) wait for real time, a few hundred milliseconds each; every other test synchronises on the work it started.

## Risks

| Risk | Mitigation |
| --- | --- |
| PgBouncer is not Hyperdrive; a passing probe says nothing about Hyperdrive | The catalogue's Hyperdrive column is `docs`, `unverified` or a recorded run only; the probe Worker is a wizard |
| Probes are timing-sensitive (cancel, abort, deadlock) | Each synchronises on an observable event (the statement is active, both transactions hold their first lock); the abort probe waits 500 ms for the server to notice a closed socket, the one fixed delay |
| `libpg-query` is a WebAssembly build of the PostgreSQL 18 parser; it runs in Node and CI, not in workerd | The lint is a CI and CLI tool; the core, which runs in workerd, does not import it |
| The catalogue goes stale (Hyperdrive's docs changed on 2026-10-28) | Every row has its source; the README says when a cell came from where; re-reading the sources is the owner's job and a PR |
| The Effect hang (M2b) is not reproduced | Said in the row and in the pin; the Effect adapter's spec reproduces it with its own client |

- **2026-10-29, plan written** with the build.
- **2026-10-29, build deviations (found while building; none changes the journey or a falsifier).**
  1. **Cells carry their own `verifiedBy`** (the assignment lists "verified-by" as a row field). A row is verified differently per column (the direct cell is `docs`, the PgBouncer cell a probe, the Hyperdrive cell a recorded run or nothing), so one value per row would say less. The README shows `outcome (verifiedBy)` per cell.
  2. **The M2b hang is not reproduced; the class is.** With node-postgres, `max_prepared_statements = 0` ends in 42P05 errors and wrong answers (a shared name runs another client's SQL), not in a hang. The hang needs `@effect/sql-pg` (Effect), which only the Effect adapter package may depend on. The catalogue row, the pin and the roadmap say so; the Effect adapter spec reproduces it.
  3. **Rule relaxations in `vite.config.ts`**, each with its reason there: `eslint/require-await` and `unicorn/no-await-expression-member` off everywhere; sequential-step rules (`no-await-in-loop`, `promise/*`, `no-array-reduce`) off for the harness and tests; `no-runtime-typeof`, `no-bitwise` and `no-object-parameters` off for the lint's parse-tree code; `no-template-curly-in-string` off for tests whose fixtures are source text. They are rule switches, not suppression directives, so the exception registry has no entry for them.
  4. **The catalogue's Hyperdrive evidence is another project's run**, excerpted into `docs/evidence/hyperdrive/` with its source commit, not a probe of this repository. Four rows use it (`request-abort`, `savepoints`, `on-conflict`, `sqlstate-passthrough`).
  5. **The harness found that node-postgres hides the SQLSTATE of a server-side FATAL** (idle-in-transaction timeout, transaction timeout): the error arrives as an `'error'` event on the client, and a later query fails with "Client has encountered a connection error and is not queryable" and no code. The harness session keeps the first such event and throws it. The `pg` adapter (spec 0002) must do the same.
