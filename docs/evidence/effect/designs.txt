Reading:

- A transaction (an insert, then `pg_sleep(30)`) is interrupted once the observer, a separate client on PostgreSQL itself, sees
  the statement running. With design A no backend is busy when `Fiber.interrupt` returns: the interrupt waits for the cancel and
  the rollback. With design B (an Effect around the pg adapter, abort by `AbortSignal`) the backend is still busy when the
  interrupt returns and is gone 600 ms later: the interrupt returned before the transaction was over.
- M2b: the plain PgClient with its default `prepare: true` behind `max_prepared_statements = 0` committed 6, 17 and 20 of 800
  and then hung until it was killed: the number that commit before the hang varies from run to run, the hang does not (the
  research report measured 798 of 800 and a hang on 4.0.6). The layer for `pgBouncer(0)` sends no named statement and
  completes. Behind `max_prepared_statements = 1000` both complete.

Scratch runs before the script existed (same machine, same versions, scripts not kept): the plain PgClient with `prepare: true`
behind max_prepared_statements=0 committed 15 of 800 (798 had ended and 783 of those with "PgConnection: Query failed"; a
60-transaction run showed the cause of the failures: SQLSTATE 26000, "prepared statement ... does not exist"), and committed
800 of 800 with prepare false (0) and with 1000 for either setting.
